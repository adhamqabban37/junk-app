# Project Memory: AI Salvage Yard Intelligence Platform

## Decision Log
- **Date: 2026-07-30 (Final Verdict)**
  - **Architecture:** Consolidated a hybrid approach from two research blueprints.
  - **Backend:** Settled on **NestJS + Node.js** for a unified TypeScript stack with strong event-driven capabilities (BullMQ).
  - **Frontend:** Committed to a **PWA with IndexedDB and Background Sync** to handle the hostile networking environments of salvage yards.
  - **Database:** Standardized on **PostgreSQL + pgvector + RLS** from day one to prevent migration pain.
  - **AI Strategy:** Defined a two-stage evolution: Pure Gemini (Phase 1) $\rightarrow$ Hybrid YOLO/Segmentation/Gemini (Phase 3).
  - **Data Strategy:** Minimalist start with **NHTSA (Free)** and **CSV Exports** to minimize early costs and dependencies.
  - **The Moat:** Explicitly decided to capture all `[AI Prediction $\rightarrow$ Human Correction]` pairs to build a proprietary salvage-yard dataset.
  - **Scoping:** Intentionally excluded NMVTIS and Full YMS replacement from the MVP to focus on the "Photos to Inventory" thesis.

- **Date: 2026-08-06 (Bulk photo scan / AI multi-part detection)**
  - **Flow direction:** Added a **photo-first** path alongside the existing **part-first** one, rather than replacing it. Part-first works offline; photo-first cannot, because detection needs the server.
  - **Detection is stateless.** `POST /ai/detect-parts` writes nothing to the database. During intake the vehicle exists only as an IndexedDB draft, so there is no `Vehicle`/`Part` row to attach to. Confirmed detections enter the draft client-side and reach the DB through the existing `POST /vehicles/intake`, leaving the whole sync + review path unchanged.
  - **Human-in-the-loop placement:** the **worker confirms on the phone**, not the manager at the desk — they are standing at the vehicle and can look at it. (Supersedes an earlier note in PROGRESS.md that assumed manager-side confirmation.)
  - **Ambiguity is surfaced, never guessed.** A detection whose side is unknown offers its candidates; one whose side contradicts every candidate is reported unmapped. Rationale: a wrong part number in inventory is worse than an unresolved one.
  - **Unmapped detections are kept, not dropped.** A dropped detection is invisible to the worker — they'd never know the AI saw it.
  - **Per-photo grades, carried through sync.** `PartDraft.detections[]` is keyed by photo, not by part, and the server persists these instead of re-grading. Re-running the single-part prompt on a multi-part scene photo would stamp one arbitrary grade onto every part in it.
  - **LHD assumption** baked into the taxonomy matcher (`driver`=left, `passenger`=right), because the taxonomy itself mixes conventions (`Door (Driver Front)` vs `Fender (Left)`). Wrong for RHD markets — making it configurable is a real change, not a tweak.

- **Date: 2026-08-08 (Manager-side "add photos to an existing vehicle")**
  - **Re-grading is a side effect of uploading, not a separate action.** `POST /parts/:partId/images` enqueues an AI job and a successful grade forces `Part.status = PENDING_REVIEW`. There is no re-grade endpoint and none was added. Consequence worth remembering: **adding a photo to an already-approved part pulls it back into the Review Queue** — intended, and surfaced in the UI rather than left as a surprise.
  - **Manager and worker got separate screens** (`(desktop)/vehicles/[vehicleId]` vs `(mobile)/previous-vehicles/[vehicleId]`) despite calling the same three endpoints, because they answer different questions: re-shoot-this-part at the car vs which-parts-are-stuck at a desk. Only the manager screen has the missing-photos summary.
  - **No new backend endpoints or role changes.** Every route needed was already open to any authenticated role; verified against the live API (manager token → 400 for a missing file, not 403) instead of trusting the guards by reading them.

- **Date: 2026-08-08 (VIN-driven scan on the manager screen)**
  - **The VIN drives the expected parts list, and it is a heuristic — say so.** `Vehicle.decodedRaw` already stores all 140 NHTSA variables; `Body Class` + `Doors` are enough to derive which exterior panels exist. This is **not** fitment data (that's ACES/Hollander, licensed, out of scope). Anything the decode can't determine is left OUT of the expected list, never guessed — a checklist naming parts the vehicle never had can never be completed.
  - **The roster is fed to Gemini, not just used after it.** Pinning the model's vocabulary to the taxonomy's own wording took the live run from "rear doors/grille/windshield unmappable" to **0 unresolved out of 38 detections**. Constraining the matcher to the roster additionally makes a coupe incapable of producing a "rear door".
  - **Automatic filing, with the human gate moved rather than removed.** The user chose no per-detection confirmation. Parts land `pending_review`; approval before export is the gate. Confidence below the tenant threshold files the part and photo but writes **no grade** (`needs_manual_grading`); ambiguous/unmapped create **no Part at all** and are returned for a person.
  - **A poor photo must still produce parts.** The scene prompt now reports `image_quality` and is told explicitly that low clarity is not a reason to return nothing. The field is optional in the schema so a model omitting it can't fail the whole response.

- **Date: 2026-08-12 (Car-Part.com becomes the Phase 1 syndication target)**
  - **Decision:** Car-Part.com is now the **primary Phase 1 publishing destination**, moved up from Phase 2. eBay and Shopify stay in Phase 2. Rationale: Car-Part.com is where salvage buyers actually search for recycled OEM parts; eBay is a general marketplace that happens to carry them.
  - **This overturns a deliberate deferral, not an oversight.** `BUILD_PLAN.md` §GSTACK/CEO listed Car-Part under "not in scope (correctly deferred)" and `ARCHITECTURE.md` §5 put it under "Scale". Those were reasoned positions; they are superseded by product direction, and the reasoning that made them right still applies as *cost*, below.
  - **Interchange is the load-bearing dependency, and it reverses `ARCHITECTURE.md` §5's "avoid Hollander early".** Car-Part.com's search model is interchange-based — a buyer finds a part because its interchange number matches. Car-Part's own inventory tool (Partmate) advertises "decodes interchange from the VIN". A part with no interchange number is close to invisible on the platform, so "publish to Car-Part" and "avoid interchange licensing" cannot both hold. **Preferred resolution: license Car-Part Interchange from Car-Part.com as part of the recycler agreement** rather than taking on Hollander — to be confirmed with them, see below. This also settles the long-flagged ARCHITECTURE-vs-DESIGN_SPEC contradiction (PROGRESS.md) in favour of *interchange is now in scope*.
  - **The feed spec is behind an NDA, so the exporter cannot be written yet.** Car-Part.com's recycler registration is: registration form + non-disclosure agreement → they issue credentials → those unlock upload instructions *specific to your platform*. Until that lands, any Car-Part export code is guesswork. **Do not write the exporter against an assumed format.** (Sourced from a search snippet, not a page read directly — `car-part.com` 403s automated fetches. Confirm with them by phone.)
  - **Their standards replace ours at the boundary, and two of ours don't match.** Car-Part expects **ARA damage codes** (structured location + type + repair-hours, e.g. `5P1` = parking-lot ding, ~1hr) where we emit free text (`misalignment`, `scuff`, `obscured`), and **ARA grades A/B/C** where we have just added a fourth grade, **D**. ~~Decide whether D is internal-only and maps to C on export, or whether the rubric returns to three grades.~~ **Resolved 2026-08-12: keep A/B/C/D internally and map at the export adapter** — see the 2026-08-12 architecture entry below. The Grade D chunk is unblocked for commit.
  - **Price stops being optional.** `PartsService.exportCsv()` has always emitted a hardcoded empty `price` column. Every marketplace requires a price; this is now a blocker rather than a placeholder, and it is the one piece of the work that does **not** depend on the NDA'd spec.
  - **Competitive note worth remembering:** Partmate (VIN → interchange portable inventory) and Photomate (mobile photo/inventory) are Car-Part.com's own tools and overlap this app's core loop directly. The differentiator is AI grading and the correction Moat, not the act of inventorying.

- **Date: 2026-08-12 (Architecture refinement — canonical inventory, phases 1 & 2)**
  - **Scope was held deliberately: "a small architectural improvement, not a new product."** The AI inspection workflow, offline-first intake, correction moat, multi-tenancy/RLS and the PWA were explicitly out of bounds. Several genuinely better models were designed and then **declined as over-scoped** — a `Yard` entity, a hierarchical `StorageLocation` table, separate `ConditionAssessment`/`PartCondition` tables, a polymorphic `Image`+`ImageSubject`, and renaming `Part`→`InventoryItem`. Worth knowing they were considered and why they were dropped, so they aren't re-litigated as oversights.
  - **The `PartType` / `InventoryItem` split people keep asking for already exists.** `PartTaxonomy` *is* PartType and `Part` *is* InventoryItem. The problem was never the split — it was that `Part` was too thin and the taxonomy encoded side inside its display string. Renaming the tables is pure code churn for zero customer value and is **no cheaper now than later**, so it was declined.
  - **`AiAnalysis` is append-only. Never update a row there.** Corrections used to be written onto the analysis, which corrupted the training context of every `HumanCorrection` joined to it. The human's answer now lives on `Part.final*` and readers resolve both through `parts/effective-condition.ts`. This is the single highest-value change of the session and it needed almost no schema — the *behaviour* was the fix.
  - **Condition resolution is per field, and NULL is the only "unset" signal.** A human-set empty damage list is a real answer and must beat the AI's tags; treating empty as absent silently restores damage a manager cleared.
  - **Prompt versions are content hashes, not hand-maintained strings.** A version nobody remembers to bump is worse than none: it asserts two predictions shared instructions when they did not. Editing `GRADING_RUBRIC` therefore changes both prompt versions, which is correct.
  - **Stock numbers: per-tenant counter on `tenants`, not a Postgres sequence** (sequences are global), claimed with `increment()` inside the intake transaction so the row lock serializes concurrent claims. Issued **after** the idempotency check, so a retried sync cannot burn a number and leave a gap.
  - **`FIRST_STOCK_NUMBER = 1000` is a one-way door.** Trivial to change until a customer prints a label; effectively permanent after.
  - **Internal grades do not bend to marketplaces.** Keep A/B/C/D internally and map at the export adapter. This is what unblocks committing Grade D without knowing any external standard, and it is the general rule: canonical inventory is never designed around a specific marketplace.

- **Date: 2026-08-15 (Gemini resilience, angle classification, the review-queue photo)**
  - **Ask the model about a *set* when the question is comparative.** Vehicle angle classification is one call per chunk of 12 photos, not one per photo, because "which side of the car is this?" is answerable from a set (two photos share a dent; the side without the fuel door is the other one) and close to a guess from one frame. The opposite of part detection, which is per-photo because each photo is an independent scene. Cheaper as a side effect, not as the reason.
  - **Only retry what can succeed on a retry.** `GeminiRequestError` carries `retryable`; 429/500/502/503/504 wait and retry, a malformed response or bad request throws immediately. Retrying a deterministic failure is three times the cost and the same answer.
  - **Model aliases are load-balanced independently, so a fallback model is a real fix, not a hedge.** Observed: `flash-latest` timing out while `flash-lite-latest` answered in 566ms. Tried only after the primary exhausts retries on a retryable failure.
  - **A per-attempt timeout is a UX requirement, not a nicety.** An overloaded call was measured at 43 seconds before returning 503, with the worker watching "Analyzing photos…" the whole time.
  - **A human gate with nothing to look at is not a gate.** The review queue asked managers to approve AI grades while showing no photo. Whenever a screen exists to let a person disagree with the AI, check that it shows them what the AI saw.

## Pitfalls & Lessons
- **A migration doing DML on an RLS table silently affects ZERO rows.** Every tenant-scoped table has `FORCE ROW LEVEL SECURITY`, which binds the table **owner** too. Migrations run as `junkyard_app` with no `app.tenant_id`, so the policy resolves to NULL and the table looks empty — a plain `UPDATE vehicles SET ...` reports success and changes nothing, with no error. Set tenant context per tenant and update that tenant's rows, exactly as the app does (`1786330000000-AddVehicleIdentityAndAcquisition.ts` is the reference). Do **not** `DISABLE ROW LEVEL SECURITY` around a backfill: it works, but it normalizes turning tenant isolation off inside a migration and the next person may not turn it back on.
- **A test that tears down in its own body leaks into every test after it.** `sync.test.ts` called `unregister()` as the last statement of each test, so one failed assertion left a live store subscription — and its client — running for the rest of the file, and a later test asserting `sync_failed` saw `synced` from a client it never created. Teardown belongs in `afterEach`. The general shape: **when one failure produces two, suspect leaked teardown before suspecting two bugs.**
- **Prove a flake fix instead of re-running until green.** The `sync.test.ts` cascade was confirmed by *deliberately forcing* the first test to fail and comparing: 2 failures unfixed vs. 1 fixed, with the collateral failure landing at the same test and column as the original. That is evidence; three consecutive passes is not.
- **`eslint --fix` can strip a type assertion and create errors.** `no-unnecessary-type-assertion` deleted an `as T` on a raw `manager.query()` result (assertions on `any` read as redundant), which then tripped `no-unsafe-assignment`. If a cast keeps vanishing, that rule is why — and the better answer is usually to stop using raw SQL, not to fight the linter.
- **Shared reference data doesn't cascade.** `part_taxonomies` has no RLS and no FK from `Tenant`, so an e2e suite deleting its tenant does **not** reclaim taxonomy rows it created. Two suites leaked 16 rows into the dev DB this way over ~12 runs and polluted every worker's real part picker. Any test creating a `PartTaxonomy` must delete it explicitly.
- **Don't trust a diagnosis in the backlog without re-deriving it.** The duplicate-taxonomy item blamed `seed:taxonomy` having no upsert guard. It has had one since day one. The real cause was elsewhere entirely, and the "obvious" fix would have changed nothing.
- **Windows will answer requests to a disconnected adapter's stale IP.** A local `curl` against `192.168.1.193` succeeded while that Wi-Fi adapter was `Disconnected` — so "I tested it locally and it works" is *not* evidence a phone can reach it. Confirm with `Get-NetAdapter`.
- **Secure-context APIs are the recurring tax on LAN HTTP testing, and they fail differently.** Two hit this project:
  - **`getUserMedia`** — no camera over plain `http://`, ever, on any device. No workaround short of an HTTPS tunnel. File inputs are unaffected.
  - **`crypto.randomUUID()`** — also secure-context only, and it took out *every* intake screen on the phone with `crypto.randomUUID is not a function`. Unlike the camera this one IS fixable: **`crypto.getRandomValues()` is not secure-context gated**, so a hand-rolled v4 UUID from it is just as sound (`frontend/src/lib/random-id.ts`).
  Before testing anything on a phone over LAN HTTP, grep for secure-context APIs first — `crypto.subtle` and the Clipboard API are the same class and are not yet used here.
- **A white page on a phone is probably Next blocking dev resources, not your code.** Next 16 refuses `/_next/*` and HMR to any origin other than the one the dev server started with, so the HTML renders and every chunk 403s — blank screen, no on-screen error, and the only evidence is a warning in the dev server's own log. `allowedDevOrigins` in `next.config.ts` fixes it. Check the server log before debugging the app.
- **Live runs find what tests don't.** Every session so far has had this shape: the suites go green, then the first real use finds real bugs (2026-08-02 found two, 2026-08-06 found two more in the first live detection call). Treat "tests pass" as necessary, not sufficient.
- **One symptom can be two bugs, and that's why it looks unfixable.** The e2e "flake" was a test-level BullMQ teardown race *and* a native `0xC0000409` crash at similar rates. Fixing either alone still left the suite red ~1 run in 3, so every prior fix attempt looked like it had failed. **Measure the failure rate before and after (30 runs, not 1)** — a single clean run proves nothing, and a still-failing run doesn't prove your fix was wrong.
- **Check whether a "cross-file" flake reproduces in one file alone.** The BullMQ race was described as a cross-file teardown race in every doc and code comment for months; `app.e2e-spec.ts` reproduced it running by itself, 2 runs in 3. The wrong framing is what stopped anyone trying the cheap experiment. Its real cause: BullMQ's `RedisConnection` constructor emits `'error'` when the in-flight `init()` rejects, while `close()` has already called `removeAllListeners()`. Await `connection.client` (the `initializing` promise) before closing.
- **Registering `process.on('uncaughtException')` does not stop Jest failing the test.** Node invokes *every* listener, so Jest's own handler still records the error against whatever test is running. Such a handler suppresses only Node's crash-the-process default — it is not a way to swallow a teardown error.
- **The taxonomy leak has a structural cause, not a per-suite one.** Every e2e suite deletes its tenant *then* its taxonomy row, so **any** throw in the tenant delete skips taxonomy cleanup — and the native `0xC0000409` crash kills Jest mid-run, skipping `afterAll` entirely. That is why leaked rows keep reappearing after being "fixed" twice. Delete taxonomy **before** tenants (safe once the suite's vehicles are gone), and find-or-create rather than blindly creating: CI runs migrations *without* `seed:taxonomy`, so a suite needing seeded rows must make its own and delete only what it made.
- **A verified-clean `tsc` goes stale.** `vehicles-intake.e2e-spec.ts` had a type error while all 77 e2e tests passed (an `await` on a sync predicate is fine at runtime). Green tests are not evidence the typecheck is green.
